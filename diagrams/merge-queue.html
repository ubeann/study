01 What it is

A merge queue is a bot that merges approved pull requests into a busy branch first-in, first-out, after testing each one on top of the latest base branch plus the PRs ahead of it. A PR that passed CI only proved it works against the main it was tested on; the queue tests the main it will actually land on.

02 The usual ways vs the queue

Merge manually, no rule

PR A renames getUser() to fetchUser(); PR B adds a caller of getUser(). Both green on the old main. Merge A, merge B: main is broken, and nobody ever ran A + B together.

"Require branches to be up to date"

Safe, but every merge makes every other open PR stale. Each author clicks "update branch", waits for CI again, and races the next merge. Three PRs with 20-minute CI cost about 70 minutes and a human watching each one.

Merge queue

Click "queue" and walk away. The bot builds temporary branches, runs CI on the exact future main, merges what passes, and drops what fails without blocking anyone else. GitHub: same benefits as the up-to-date rule, without the author updating the branch.

03 How it flows (GitHub)

PR passes branch checks→ added to queue→ temp branch: latest main + PRs ahead + this PR→ merge_group webhook, CI runs→ required checks pass: merged→ fail or timeout: removed, rest rebuilt

Workflows must add on: merge_group next to pull_request; without it the required check is never reported and the merge fails. Knobs: build concurrency 1 to 100, min/max PRs per merge 1 to 100 plus a wait time, status-check timeout.
