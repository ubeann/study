01 What it is

Scion is Anthropic's in-house, server-centric source control system, built when Claude-driven merges outgrew git infrastructure sized for humans. It runs the company monorepo in production but is not released: "by no means a suitable replacement for git for general use."

May 2026: ~2,500 merges/day→ Sep 2026: 30,000+ merges/day· ~100 GB history, 25 GB+ working copy· ~25M CI checkouts/day: 600+ PB/day if fetched naively· several hundred git mirrors at peak

02 Git's assumption vs Scion's

Git: offline, thick clients

Every clone holds the full history as packfiles; blame, diff and merge run on the client. The fetch negotiation is "here is what I have", answered with one large packfile computed per client.

Scion: always online, thin clients

Nearly every client is a CI job or agent with a constant connection. The server owns history, blame, commits, merges and rebases; clients keep a bounded cache and an optional, sparse or virtualized working copy. Many jobs (bisect, revert) just call the API with no checkout.

Git commit

Points to a snapshot of the whole tree. Refs move as part of the commit flow; a merge queue serializes landings behind a global lock.

Scion changeset

An entry in a write-ahead log listing only the files changed relative to the first parent, with content-addressed blob pointers. Cheap, incremental, lock-free; refs discouraged except main and release branches. Derived data (blame, path history, skip lists) is computed recursively from the parents' values.

03 How a fetch flows: "here is what I want"

client asks for the root tree→ checks local store for missing subtrees, requests them recursively→ fetches only the blobs it needs→ small, cacheable, resumable responses→ skip a subtree = sparse checkout for free
