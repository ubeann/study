01 What it is

Starlark (formerly Skylark) is a small configuration language with Python 3 syntax, designed at Google to describe builds. Bazel is the open-source flavour of Google's internal build tool Blaze; every BUILD file and every .bzl extension in Bazel is Starlark.

02 The usual way vs this

Usual way: a real scripting language

Build files are Python, Groovy or shell. Anything goes: read the clock, hit the network, mutate globals, loop forever. The build tool cannot prove two runs are equal, cannot evaluate files in parallel, and cannot parse the file without running it.

Starlark: Python minus the dangerous parts

No I/O, no clock, no while, no recursion, no classes, no exceptions, no mutable globals after load. Same input, same output, every time. Files load in parallel and freeze, so the build tool can cache them and tools can rewrite them.

03 How a Bazel build flows

load .bzl + BUILD (Starlark runs, macros expand)→ analysis: rule implementations emit actions→ execution: run actions in sandboxes, hit caches

Starlark only ever runs in the first two phases. It describes the graph; it never compiles anything itself.

05 When to use it

Use it whenSkip it when
Large codebase, several compiled languages, many platforms, lots of tests: the cases Bazel's FAQ names.A small single-language project where the native tool (cargo, go, npm) already gives you reproducible builds.
You need a config language that users can extend but that can never do I/O or hang: Buck2, Copybara, Tilt, Drone, lucicfg all picked Starlark for this.The script needs the network, the clock, or heavy computation. Starlark's own design doc says CPU-heavy work belongs in another language.
You want tools to parse and rewrite the config files, not just run them.Build steps whose outputs must not be cached, or a few long sequential steps that cannot be split.
