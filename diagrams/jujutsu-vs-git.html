01 What it is

Jujutsu (jj) is a Git-compatible version control system that uses a Git repository as its storage layer. Your teammates and GitHub see ordinary commits; what changes is the local model: the working copy is a commit, commits have a stable change ID, descendants rebase automatically, conflicts are stored instead of stopping you, and every operation can be undone. The README calls it experimental, with on-disk format changes still possible before 1.0.

02 Git's model vs jj's

Git: four places for code

Working dir → git add → index → git commit → commit, plus git stash. Switching tasks mid-edit means a stash or a throwaway WIP commit.

jj: one place, commits

Your edits live in the working-copy commit @. Most jj commands snapshot it automatically; new files are tracked implicitly, .gitignore is honoured. Switching tasks is jj new; nothing to stash.

Git: the hash is the name

Amend "Add login" and a1b2c3 becomes 9f8e7d. Anything that pointed at the old hash is stale.

jj: change ID + commit ID

The change ID (e.g. kxqp) "stays the same when the commit is rewritten". The Git commit ID still changes underneath.

Git: a conflict halts the rebase

Repo sits in "rebase in progress" until you resolve or --abort. Other branches built on the edited commit are rebased by hand.

jj: conflicts are data in the commit

A conflicted rebase "will succeed"; the conflict is recorded in the commit and can be resolved later. Descendants of a rewritten commit are rebased automatically.

03 Fixing a bug in the bottom of a stack A → B → C

Git: stash→ rebase -i, mark A edit→ fix, add, commit --amend→ rebase --continue→ resolve conflicts now or abort→ stash pop
jj edit A→ fix the file→ B and C rebased for you→ jj edit C to go back

If the fix conflicts in B, the rebase still finishes: B and C carry a conflict marker in the log. Resolve B later with jj new B, fix, jj squash; C is rebased again.
